# Oxyde architecture

Status: **draft**. This document records design decisions; change it in the same pull request as any code that deviates from it.

## 1. Guiding principles

1. **Rust owns the application; C++ owns only the geometry kernel.** All modeling logic — sketches, constraints, the feature tree, naming, file I/O, UI — is Rust. C++ exists solely in a thin shim around OpenCASCADE (OCCT).
2. **The kernel is replaceable.** Everything above `oxyde-kernel` talks to a Rust trait, never to OCCT. A future pure-Rust kernel (in-house, or one built on `truck`) must be a drop-in backend.
3. **The model is data; geometry is a cache.** A part is its feature tree. B-rep solids are derived by replaying that tree and may be discarded and rebuilt at any time.
4. **Rebuilds are deterministic.** Same feature tree + same kernel version ⇒ same topology, same persistent names. `crates/oxyde-tests/tests/determinism.rs` rebuilds parts made of several booleans ten times and compares every face, edge, name and history run to run.
5. **Open formats in and out.** Native files are documented (`FORMAT.md`); exchange uses STEP and friends.

| Crate | Depends on | Must never depend on |
|---|---|---|
| `oxyde-geom` | — | anything else in the workspace |
| `oxyde-sketch` | `geom` | `kernel`, `occt` |
| `oxyde-kernel` | `geom` | `occt`, `model` |

| `oxyde-model` | `geom`, `sketch`, `kernel` | `occt`, `app` |

| `oxyde-render` | `kernel` (mesh types only) | `occt`, `model`, `app` |
| `oxyde-sim` | — | anything else in the workspace |
| `oxyde-app` | all of the above | — |
| `oxyde-cli` | `format`, `model`, `occt`, `kernel`, `render` | `app`, `eframe` |
| `oxyde-tests` | `model`, `occt`, `cli` (dev only) | — |

`oxyde-sim` (the Simulation tab's mesher and solvers, and generative design's on a grid of voxels) stands alone like `oxyde-geom`: it takes plain triangle meshes with face labels and gives back numbers, so the application turns the kernel's meshes and the persistent names of fixtures and loads into labels, and a better mesher or solver can replace its parts without touching the rest (`docs/SIMULATION.md`).

`oxyde-app` and `oxyde-cli` are the only places where a concrete kernel backend is chosen. `oxyde-tests` holds end-to-end tests that drive the model through OCCT, so neither crate has to depend on the other.

`oxyde-cli` (`eval`, `check`, `export`, `snapshot`, `drawing`) is the headless path through the same code as the application: `oxyde_format::load_part`, `Part::from_definition`, `Part::rebuild` with an `OcctKernel`, the kernel's `volume`, `centre_of_mass`, `bounds` and `topology_counts`, `Kernel::export_step`, `Kernel::export_iges`, `oxyde_format::stl`, `oxyde_format::obj` and `oxyde_format::threemf`, `oxyde_render::snapshot` (the software renderer, with `oxyde_render::mesh_deflection` for the application's display precision), and `Kernel::project_edges` with `oxyde_format::drawing` for drawings. It is a library with a thin `main`, so `oxyde-tests` runs the commands in-process (`crates/oxyde-tests/tests/cli.rs`: a filleted box whose measures are known by hand, and the STEP cart). Its JSON (`Evaluation`: `file`, `ok`, `features[name, type, status, message]`, `bodies[name, created_by, volume, area, centre_of_mass, bounds, faces, edges, vertices]`, `total`) and `expected.json` (`Expected`) are interfaces for scripts and the reference oracle, so their field names stay put.

## 3. The Rust ⇄ C++ boundary (`oxyde-occt`)

```
crates/oxyde-occt/
├── build.rs        # locates OCCT (and Netgen, if any), compiles cpp/ with the cxx bridge
├── cpp/
│   ├── shim.h      # coarse-grained C++ API, no OCCT types in signatures
│   ├── shim.cpp    # implementation against OCCT
│   ├── netgen_mesh.h    # Netgen behind a plain C++ interface (no Netgen types)
│   └── netgen_mesh.cpp  # the only file that includes Netgen's headers
└── src/
    ├── ffi.rs      # #[cxx::bridge] declarations
    └── lib.rs      # impl oxyde_kernel::Kernel for OcctKernel
```

Rules:

- **No OCCT type crosses the boundary.** Shapes live in a C++-side arena; Rust holds opaque integer handles (`ShapeHandle(u64)`). Data crosses as plain structs (`f64` arrays, enums, strings).
- **Coarse operations only.** The shim exposes on the order of 50 functions (make prism, revolve, boolean, fillet, shell, tessellate, read/write STEP, …), not OCCT's API surface.
- **Every operation returns its history.** OCCT's `BRepBuilderAPI_MakeShape::Generated / Modified / IsDeleted` results are returned alongside the new shape. This is the raw material for topological naming (§6).
- **Results are checked.** OCCT's builders can report success on geometry they could not really make: shells, fillets and chamfers are checked with `BRepCheck_Analyzer`, and each wall of a shell must lie the wall thickness from the face it copies (a wall thicker than a face's curvature comes out turned inside out, which `BRepCheck` accepts).
- **No C++ exceptions escape.** Each shim function catches `Standard_Failure` (which does not derive from `std::exception`) and everything else, and rethrows a `std::runtime_error` that `cxx` turns into a Rust `Err`. The shim is compiled with `/EHsc` on MSVC (build.rs): without it MSVC runs no destructors while an exception unwinds, so a failure thrown through the shim would leak every local on the way out, the STEP lock and the arena's lock included.
- **One arena, a kernel per thread.** Shapes live in one arena shared by every `Session` of the process (a map behind a mutex, held only to copy a reference-counted `TopoDS_Shape` handle in or out), so a `ShapeHandle` is valid in every kernel. `OcctKernel` itself is `!Send` and stays on the thread that made it; another thread opens a kernel of its own with `Kernel::open_worker`, rebuilds a part with it, and hands the handles back. OCCT's modelling algorithms and mesher are safe on different shapes from different threads; two threads must never touch the same shape at once (meshing stores triangulations on the faces), so a part belongs to one thread until it is handed over. Within one boolean the shim lets OCCT use every core as well (`SetRunParallel`): the intersections of the face pairs are computed in parallel and the result assembled in the same order as in serial mode, which the determinism test checks; a section cut through a 2400-face imported solid takes 5–35% less time, a third on its slowest plane. The STEP translators and the XCAF application are not thread-safe at all: the shim runs every STEP read and write under one lock (see "STEP assembly import" below). The application uses this to load the parts of an assembly on every core (`assembly::load_many`); a long rebuild still blocks the UI thread until the application moves it to a worker and reports progress through a channel.

- **Netgen meshes volumes, nothing else.** `Kernel::volume_mesh` hands one solid to Netgen's OpenCASCADE interface (`netgen::OCCGeometry`, its surface and volume mesher, optimisation, then `MakeSecondOrder`, which puts each new edge node of the boundary on the true face). Netgen is LGPL-2.1 and linked as a shared library (`nglib`, `ngcore`), so it can be replaced in a bundle (BUILDING.md, THIRD-PARTY.txt). Its headers bring `using namespace std`, macros and globals, so they are compiled in `cpp/netgen_mesh.cpp` alone, which returns plain vectors to `shim.cpp`; Netgen keeps global state, so meshes are made one at a time behind a lock of their own. Netgen has no progress callback: while a mesh runs, a watcher thread in `netgen_mesh.cpp`, made and joined under that lock, copies Netgen's task and percent (`netgen::multithread`) to a `MeshMonitor` and turns its stop request into `multithread.terminate`, which Netgen's loops check; only the mesh holding the lock touches those globals, so stopping one mesh never stops the next. `volume_mesh_watched` reads the monitor from a Rust thread every 100 ms, maps Netgen's tasks to six stages of one fraction that never goes back, reports it to `MeshWatch::progress` and passes `MeshWatch::cancel` on (`VolumeMeshError::Cancelled`). The shim converts nothing: Netgen's node order and its face numbering (its own face map) come out as they are, `shim.cpp` maps each face to its index in the shape's topology (`TopExp::MapShapes` order, what `topology` and persistent names use), and `src/lib.rs` reorders the edge nodes and checks every element's orientation instead of relying on Netgen's conventions. Netgen is optional: without it (not found, or `OXYDE_NETGEN=0`) the shim is built without `OXYDE_NETGEN`, `has_volume_mesher` is false, `volume_mesh` returns `VolumeMeshError::Unsupported`, and the Simulation tab falls back to `oxyde-sim`'s own lattice mesher.

Toolchain: `cxx` / `cxx-build` for the bridge and to compile the shim. **Windows/MSVC only for now.** `build.rs` locates OCCT through `OXYDE_OCCT_DIR`, `VCPKG_ROOT`, or explicit `OXYDE_OCCT_INCLUDE_DIR` + `OXYDE_OCCT_LIB_DIR` — see `BUILDING.md`.

### Never crash

A panic in a modelling or UI path would take the unsaved document with it, so not crashing outranks a feature. The C++ side already turns every OCCT exception into an `Err` (above); the Rust side has three layers under it, each catching what the one before let through:

1. **No panics written.** Every production crate root denies `clippy::unwrap_used`, `expect_used`, `panic`, `unreachable`, `todo` and `unimplemented` (and warns on `indexing_slicing`); tests are exempt. `oxyde-sim`'s numerical modules allow `indexing_slicing`, each saying why: the indices are its own, made by its mesher or checked by `TetMesh::validate` before a solve, and the application runs it on a thread under `catch_panic`, so a bug fails the study, not the window. Where a value cannot be missing, the code still says what happens if it is: an error returned (`?`, `ok_or_else`), or a harmless fallback with a comment. `cargo clippy --workspace --all-targets` enforces it.
2. **Kernel calls and feature builds run under a net.** `oxyde_kernel::catch_panic` runs a closure under `catch_unwind` and hands back the panic's message (the default hook still prints it to stderr). `OcctKernel` wraps every `Kernel` method in it, so a bug in the marshalling comes back as `OcctError::Internal`; `Part::rebuild` builds each feature under it too, so a panicking kernel of any kind, or a bug in a feature's own code, fails that one feature with `internal error: …` in the timeline and the rest is still built (`oxyde-tests/tests/never_crash.rs` drives the model with a kernel that panics in every operation).
3. **The document is put back.** `Document::rebuild` (`oxyde-app`) runs the rebuild under the net; a panic that gets that far may have left the part half built, so the document goes back to the last undo snapshot, the state before the change that led to the bug, and rebuilds that (without a snapshot the timeline is kept with nothing built). `OxydeApp::update` runs the whole frame under the net as well: a panic anywhere in it ends the frame, the change the frame recorded is taken back (`recover_frame`), and a window says that an internal error happened and that the change was undone, with the panic's message to report. A frame that fails three times in a row fails because of what is open, so the sketch session and the open command are closed, which leaves the menus to save from. Work on job threads (`jobs.rs`) is already apart: a panic there ends the job, reported as failed.

The guard is not a licence: a caught panic is a bug to fix, and tests still fail on it.

## 4. The `Kernel` trait (`oxyde-kernel`)

Implemented (see `crates/oxyde-kernel/src/lib.rs` for the documented signatures):

| Group | Methods |
|---|---|
| Construction | `make_box`, `extrude(plane, profile, vector)`, `revolve(plane, profile, axis, angle)`, `sweep(plane, profile, path plane, path)`, `loft(sections, ruled)` (OCCT `BRepOffsetAPI_ThruSections` through one contour per section, side faces named after the first section's segments; a default body answers `None`), `boolean(Fuse/Cut/Common, target, tool)` and `boolean_many` (several tools in one operation), `fillet(shape, edges, radius)`, `chamfer(shape, edges, distance)`, `chamfer_with(shape, (edge, face) pairs, first, second distance or angle)` (unequal chamfers; a default body answers `None`), `shell(shape, removed faces, signed offset)`, `transform(shape, rigid motion or mirror)` |
| Queries | `topology` (faces, edges, vertices with adjacency, surface/curve kind, area, centroid, planar normal, axis of a surface of revolution, line or circle axis of an edge, edge midpoint), `tessellate` (display mesh: triangles per face, polyline per edge, indexed like the topology), `volume`, `centre_of_mass`, `bounds` (exact box along the model axes), `topology_counts`, `distance(a, part of a, b, part of b)` (the shortest distance between whole shapes or their faces, edges or vertices, with the closest points: Measure; a default body answers `None`, so a backend without it needs no code) |
| Exchange | `export_step(shapes, colors, materials, path)` (colours per solid and per face go out as STEP colours, materials as names and densities), `export_iges(shapes, path)` (IGES 5.3 B-rep solids), `import_step(data)` (the solids as one shape, and the colours the file gives them: `StepImport { shape, colors }`), `read_step_assembly(data)` (product structure: each part once as its own STEP file with its colours, assemblies with placed instances) |
| Analysis | `volume_mesh(shape, options)` and `volume_mesh_watched(shape, options, watch)` (the same, reporting its progress and stopping on a cancel flag) (one solid filled with tetrahedra, four- or ten-node, as plain data: `VolumeMesh { nodes, tets, tet_edge_nodes, triangles, triangle_edge_nodes, triangle_faces }`), `has_volume_mesher`. Both have default bodies (no mesher: `VolumeMeshError::Unsupported`), so a backend without one needs no code |
| Lifetime | `release` |

Every construction operation returns an `OpResult { shape, history }`. The history lists, **for each face of the result**, where it came from:

| `FaceSource` | Meaning |
|---|---|
| `InputFace { input, face }` | an input face, unchanged, trimmed, split or merged |
| `InputEdge { input, edge }` | generated from an input edge (fillet / chamfer face) |
| `InputVertex { input, vertex }` | generated from an input vertex (corner blend) |
| `OffsetFace { input, face }` | offset copy of an input face (inner wall of a shell) |
| `ProfileSegment(id)` | side face swept (extruded, revolved or swept along a path) from the sketch segment with that id; a sweep makes one per path segment, told apart by position |
| `StartCap` / `EndCap` | the two ends of an extrusion, of a revolve of less than a full turn, or of a sweep along an open path |

A volume mesh is analysis data, not geometry: it carries no history and is never saved with the part. Its conventions are the kernel's, whatever the mesher's: every tetrahedron positively oriented (the fourth corner on the side the first three wind counter-clockwise around), edge nodes in `TET_EDGES` order (01 12 02 03 13 23, the order `oxyde-sim` uses), boundary triangles wound counter-clockwise seen from outside with their edge nodes in `TRIANGLE_EDGES` order (01 12 20), and each boundary triangle names its face by index in the solid's `Topology`, so a fixture or a load picked by persistent face name lands on the right triangles. One solid per call: parts in contact are meshed separately and joined by the solver (`oxyde-sim`), not by a shared mesh.

`transform` reports every face as the `InputFace` it is a copy of, so pattern instances can be named after the seed's faces. The kernel never remembers anything between calls; turning this history into lasting names is the model's job (§6). Still to come: BREP import/export (for an optional `.oxy` geometry cache).

A second, trivial backend (`NullKernel` / mock) lives in tests so that `oxyde-model` can be tested without OCCT installed.

## 5. Sketches and the constraint solver (`oxyde-sketch`)

Implemented (M2, solver only):

- **Entities**: points, lines, circles and counter-clockwise arcs. Lines and arcs refer to point entities, so connected geometry shares its points as in SolidWorks. Construction geometry is solved but left out of profiles.
- **Relations and dimensions**: fixed, coincident, horizontal, vertical, parallel, perpendicular, equal length, equal radius, point–point distance (true, horizontal, vertical), length, radius, angle, point on line, point on circle, midpoint, tangent (line–circle/arc). `rectangle()` adds its horizontal/vertical relations automatically.
- **Solver**: unknowns are point coordinates and circle radii (fixed points are not unknowns; arc radii are implied). Each relation contributes equations `r(x) = 0`; parallel and perpendicular compare the angle between the lines folded to ±90°, which (unlike its sine or cosine) has a slope where the lines start square or in line. Steps are minimum-norm Gauss–Newton steps `Δ = −Jᵀ(JJᵀ + μI)⁻¹r`, so an under-defined sketch moves as little as possible (the right behaviour when dragging), with `μ` raised towards gradient descent when a step does not reduce the error, and a backtracking line search; a full step that overshoots is still kept when the next step from there brings the error down (a watchdog: a line turned a long way swings away from a point that must stay on it). The equations are first split into clusters that share no unknown (fixed points tie nothing together), each solved and analysed on its own, so the cost follows the size of each contour rather than of the whole sketch. The Jacobian is exact: the residuals are written once over a number type that is either `f64` or a dual number carrying a derivative (forward-mode automatic differentiation), and each derivative only evaluates the equations involving its unknown.
- **Analysis**, from the Jacobian at the solution:
  - **degrees of freedom** = unknowns − rank;
  - an entity is **fully defined** (black) when no remaining motion (null space of the Jacobian) moves any of its parameters, otherwise under-defined (blue);
  - relations are taken in order: one adding no independent equation is **redundant**, one left unsatisfied is **conflicting**. A failed solve leaves the geometry untouched. The rank, the degrees of freedom and the null space all come from one incrementally reduced basis of the Jacobian's rows, so they always agree with each other.
- `profile_segments()` turns the solved sketch into profile curves whose segment ids are the entity ids, so face names (`F2.side[7]`) follow sketch entities. Contours that cross or touch each other, or themselves, are refused (`ProfileError::Crossing`, found exactly, not on sampled polygons), as SolidWorks refuses self-intersecting contours: OpenCASCADE would extrude them into empty or overlapping solids without complaint.

Relations have a stable `RelationId`. Dimensions are named `D1`, `D2`… in creation order, as in SolidWorks, and can be renamed. Entity ids, relation ids and default-name numbers come from counters saved with the sketch, so nothing is ever reused after a deletion.

In the model (M2b): a `Sketch` feature holds a `ConstrainedSketch`, solved during every rebuild. Conflicting relations put the sketch in error; redundant ones give a warning; an under-defined sketch is flagged in the timeline (`(-) Sketch1`, as in SolidWorks) but builds normally.

## 6. Feature tree and topological naming (`oxyde-model`)

### Feature tree

- A part is an ordered list of features (sketch, extrude, revolve, cut, fillet, chamfer, shell, pattern, mirror, reference plane/axis…), each with typed parameters and references.
- Features form a dependency DAG; editing one feature marks it and its dependants dirty, and only those are rebuilt.
- A rollback bar and per-feature suppression are model concepts, not UI tricks.
- Dimensions can be driven by equations over global variables and other dimensions (see *Equations* below).

### Timeline (implemented in `part.rs`)

- Oxyde is **bottom-up** like SolidWorks: parts are modeled on their own; assemblies (§8) place finished parts and never reach inside their timelines.
- `Part` holds the ordered features, the rollback bar and suppression flags. `Part::timeline()` returns one row per feature with its status (`Ok`, `Warning`, `Error`, `Suppressed`, `RolledBack`, `Pending`) — the data behind the timeline panel.
- New features are inserted at the rollback bar. Deleting a feature that others refer to is refused, and so is a new definition for a feature (`Part::replace_feature`, after editing it) that refers to itself or to a later feature: such a part could not be opened again.
- `Part::rebuild(kernel)` replays from the first edited feature only. After each feature it keeps the resulting `Body`: kernel shape, topology and the names of every face, edge and vertex. A feature that fails is marked `Error` and leaves the body unchanged; later features still build if their references exist.
- **Previews** (`Part::preview(kind, replacing, kernel)`): one feature built on the cached results of the last rebuild without being added — at the rollback bar, or in place of the feature it edits — and nothing after it, as SolidWorks rolls back to a feature while it is edited. The `FeaturePreview` holds the body it would make (faces named after the id the feature has or would get, so the faces it makes are told apart by `FaceKey::feature`), or its plane or axis, and its status (why it cannot be built). It may share shapes with the part's results, so it is released before the part is rebuilt. The feature builders take the features before the one built and the feature itself apart (`Context`), so a preview copies nothing.
- Features implemented: sketch (on Front/Top/Right, a planar face or a reference plane), boss/cut extrude (blind, mid-plane, through all on one side or both, up to a surface; reversible), boss/cut revolve (about a sketch line, a model axis, a reference axis, an edge or a face's axis; any angle, mid-plane, reversible), fillet, chamfer, shell (inward or outward, any faces removed), reference plane (offset from a plane or a flat face), reference axis (along an edge or a face's axis, or where two planes meet), linear pattern (one or two directions), circular pattern (equal spacing or not), mirror (of features, or of whole bodies joined to their images), loft (through one closed contour per sketch, each turned to run the same way round along the loft so it does not twist), hole (Hole Wizard: simple, counterbore, countersink; blind with a drill point or through all, at the lone points of a sketch: each the hole's half section revolved about its axis, the copies named as pattern instances keyed by the point's entity id so that a hole keeps its names when others come and go, all fused into one cut tool that patterns and mirrors copy). The Hole Wizard's ISO metric sizes (clearance fits, tap drills, counterbores, countersinks) are the application's (`hole_wizard.rs`); the model holds only the numbers.
- **End conditions** (`ExtrudeExtent`): *Through All* reaches as far as the bodies' exact bounding boxes (`Kernel::bounds`) go along the sketch normal, on one side or both; a cut or an intersection goes 1% of their size further, so it never ends on a face. *Up To Surface* (`PlaneRef`, so it depends on the face's feature or the reference plane) is a blind extrusion when the plane is parallel to the sketch; otherwise the prism is made past the plane and cut back to the half-space on the sketch's side (`BooleanOp::Common` with a box placed by `Transform::from_plane`), and the common's face history is mapped back onto the prism's, the box's face becoming the end cap, so the result is named as any extrusion. Neither has a depth, so neither has a `D1` dimension.
- **References to planes and axes** are `PlaneRef` (standard plane, flat face, reference plane) and `AxisRef` (model axis, reference axis, edge, face), resolved at rebuild against the body before the feature, like every other reference. Reference features produce no body, only a `ReferenceGeometry` (plane or axis) that later features and the viewport use.
- **Patterns and mirrors copy tool bodies**, as SolidWorks patterns features rather than bodies: an extrusion or a revolve keeps the solid it added or removed (`ToolBody`), and a pattern transforms a copy of that tool to each instance and fuses or cuts it, seed by seed. So a pattern of a hole cuts holes, even where the seed's surroundings differ. All the copies of a seed go into one boolean (`Kernel::boolean_many`): one boolean per copy redid the work on a body growing with each (a 10 × 10 pattern of holes went from 13 s to 0.8 s on a Raspberry Pi). Copies of the part's first boss, which made the first body, join that body. Only extrusions, revolves and sweeps can be seeds for now.

### Bodies (implemented in `bodies.rs`)

A part's geometry is a list of solid bodies (`Solid`: a `BodyId`, its kernel shape and its own topology), seen together as one `Body` whose topology concatenates theirs (faces of the first solid, then the second…) and whose `BodyNaming` names all of them at once. Everything that reads geometry by name or index (references, picking, highlighting, sketches on faces, assemblies) works on that merged view unchanged; `Body::solid_of_face` / `solid_of_edge` say which body something is on, and kernel operations run on one solid with local indices (`Solid::local_face`). Each feature result keeps the whole set of bodies after it; bodies it did not touch are shared with the previous result (not owned), so their shapes are freed once, by the feature that made them. Extrusions and revolves join, cut, intersect or add a new body (`ExtrudeOp`), on chosen bodies or automatically; *Combine* is a boolean between bodies. See `FORMAT.md`, *Bodies*.

### Persistent naming (implemented in `naming.rs`)

The problem: a fillet stores "edge #17"; after an upstream edit, numbering changes and the fillet attaches to the wrong edge or fails. FreeCAD spent years on this; we designed for it from day one.

1. **Faces are named by provenance**, from the kernel history:
   - `F2.side[3]`: side face that feature F2 swept from sketch segment 3;
   - `F2.start` / `F2.end`: the two caps of extrusion F2;
   - `F5.blend(edge(…))`: fillet face that F5 made from a named edge;
   - `F7.offset(F2.end)`: inner wall that shell F7 offset from `F2.end`;
   - `F9[2,0](F4.side[2])`: the copy, in instance `[2, 0]` of pattern F9, of the seed face `F4.side[2]`. Instance positions are stable while the counts grow, so a fillet on the second hole of a pattern stays on it.

   A face that a later operation only trims, splits or merges **keeps its name**, so the top face of a block is still `F2.end` after holes are cut into it. When a boolean merges faces, the name from the oldest feature wins, so existing references stay valid.
2. **Edges are named by the faces they separate**, vertices by the faces meeting at them: `edge(F2.side[2] | F2.end)`. This needs no extra history from the kernel and is stable whenever the faces are.
3. **Duplicates get a `part` ordinal** (`F2.end@1`, `F2.end@2` when a slot splits the top face), assigned in a deterministic geometric order.
4. **Resolution** of a stored name against a rebuilt body: exact match, else a unique loose match ignoring part ordinals (built with a warning), else `Ambiguous` or `Lost` (feature in error, asking the user to reselect).
5. Names reference features by `FeatureId`, never by display name, so renaming is free. Feature ids are never reused.
6. Sketches on faces get a deterministic frame (origin = projection of the model origin, x axis = least-aligned model axis), so they land in the same place after the face is resized.

Known limits, to address later: unknown-origin faces (none expected from current operations) get index-based names; when pieces of a split face swap geometric order, their ordinals swap too.

### Dimension names (implemented in `dimensions.rs`)

The groundwork for equations, SolidWorks-style:

- Every driving value has a **full name** `dimension@feature`: sketch dimensions (`D1@Sketch1`) and feature parameters (`D1@Boss-Extrude1` for the depth, `D1@Fillet1` for the radius). The name part can be changed (`Width@Sketch1`).
- Internally a dimension is a `DimensionRef { feature: FeatureId, key: Sketch(RelationId) | Feature(FeatureParameter) }`: stable ids only. Renaming a feature or a dimension changes how it is shown, never what it points to; an equation will be stored with references and displayed with the current names.
- `Part::dimensions()` lists every dimension in timeline order; `find_dimension("D1@Sketch1")` resolves a full name (quotes allowed, as typed in an equation); `set_dimension` and `rename_dimension` change one. Names are validated: unique feature names per part, unique dimension names per feature, no `@` or `"`.
- Feature dimensions are numbered per feature in the order of `FeatureKind::parameters()` (`D1`, `D2`…); optional parameters come last so existing names never shift.

### Equations (implemented in `expression.rs` and `equations.rs`)

- **Global variables** (`"Width" = 50`) and **equations** driving dimensions (`"D1@Sketch1" = "Width" * 2`), as in the SolidWorks Equations window. Syntax: numbers, quoted names, `+ - * / ^`, parentheses, `pi`, trigonometry in degrees, `sqrt abs exp log log10 int round sgn min max`. Values are in display units: mm, degrees, counts.
- Parsed expressions hold `Operand::Global(GlobalId)` or `Operand::Dimension(DimensionRef)`: stable ids again. They are printed with current names; each name reference also remembers its last known name, so an equation pointing at something deleted is still shown, saved and reported ("\"D3@Sketch1\" does not exist") instead of vanishing.
- `Part::rebuild` first evaluates everything in **dependency order** (topological sort, whatever the order of the lists), sets the driven dimensions, and only dimensions whose value really changed mark features for rebuild. A circular reference is an error on each equation involved; an error propagates to whatever uses the failed value. `Part::equation_results()` holds each value or error for the UI.
- A driven dimension is flagged (`Dimension::driven`): read-only in the Dimensions tab, shown with Σ in sketch mode, and not editable from its sketch.
- In files, expressions are stored as text with names (readable by other tools), see `FORMAT.md`.
- **Tools › Equations…** opens the window: an *Equations* tab (global variables and equations, with the value each evaluates to or its error) and a *Dimensions* tab (every dimension, rename and edit values).

## 7. Units and tolerances

- Internal length unit: **millimetre**, `f64`. Angles in radians internally, degrees in UI.
- Display units are a per-document preference; conversion happens only at the UI and file boundary.
- One central tolerance policy in `oxyde-geom` (linear `1e-6 mm`, angular `1e-9 rad` as starting values) passed to the kernel explicitly.

## 8. Assemblies (`oxyde-assembly`) and drawings (later)

- **Bottom-up**: an assembly only places parts and sub-assemblies and mates them; a component is edited in its own document (*Edit part / sub-assembly in place*, then *File › Finish editing*, which reloads the files). A part at any depth can be opened in place from the top assembly (`edit_in_place.rs`: the component is an `Occurrence`, its context the rest of the assembly in that part's coordinates through `AssemblyDoc::occurrence_placement`).
- **Sub-assemblies** are rigid, as in SolidWorks: their components stay where their own file put them, and only the top-level components are unknowns of the solver. A mate may still reach a face or edge of a part deep inside one: `MateRef::path` lists the component ids from the sub-assembly down to that part, and the app composes the placements along it (`Placement::compose`) to give the solver the geometry in the top-level component's coordinates. Loading follows sub-assemblies recursively with a stack of open files, so an assembly that contains itself is refused.
- **Components** reference part files by path relative to the assembly + document UUID, so a part moved within the assembly's folder is found again by its id (see `FORMAT.md` §6). Each component has a placement (rotation + translation, never a mirror). The first one inserted is **fixed**; any can be fixed or floated. The assembly itself (`ComponentId::ASSEMBLY`, id 0) can be a side of a mate: its standard planes, axes and origin, fixed at the identity, so a floated component can be put exactly at the assembly's origin. A mate whose both sides are fixed reports that one must be floated.
- **Mates** (coincident, concentric, parallel, perpendicular, distance, angle) name geometry the way features do: persistent face and edge names in the part, or the part's standard planes, axes and origin. `resolve` turns a reference into a primitive in part coordinates using the part's rebuilt body: a flat face is a plane (outward normal), a cylindrical or conical face its axis, a straight edge a line, a circular edge a circle (centre and normal). Each mate kind writes residuals that vanish when it holds; directions are scaled by the assembly size so that they weigh like lengths. A mate between oriented geometry is *aligned* or *anti-aligned*; a new mate starts with whichever is closest to how the parts sit. A distance between planes keeps the side the parts start on, and planes that start level part along the first one's normal; a zero distance between points or lines holds them together. An angle between planes (or circles) runs up to 180°; 0° and 180° hold the normals in line. Lines have no way round, so an angle with a line is at most 90° (150° reads as 30°, and the nearer pose is taken): between two lines it is measured from parallel, between a line and a plane from the plane, as Parallel and Perpendicular read them. Angles are compared as angles (not cosines), accurate near 0 and 180°.
- **Solver**: Levenberg–Marquardt over a small rotation and a shift per free component, from the current placements, so the answer is the nearest one (which is what dragging needs). Each component turns about the middle of its geometry (`solve_about`), not its origin: a part modelled far from its origin would otherwise swing across the assembly to meet a mate it can meet by turning in place. Mates that hold directions parallel either way (lines on an axis, a parallel mate between edges) are written as `±v − u` with the way round chosen once from where the parts start, rather than as a cross product, which is flat where the directions start square, as a screw inserted beside its hole does, and left the solver no way to turn it. Mates are first split into groups tied together through components that can move (fixed components tie nothing), each solved on its own: the cost follows the size of each group, and a conflict in one group leaves the others alone. When the mates cannot all hold, they are added back one at a time in order and each one that cannot hold with those before it is reported, as SolidWorks blames the newest mate. Where no direction lowers the error although the mates do not hold (a mate that starts on a symmetric spot, as inserted parts do: faces in line for an angle, level for a distance, points together), the slopes are measured a little way off and the step taken from there. Degrees of freedom left per component are the motions of its group that keep the mates (the null space of their Jacobian) seen on that component, so a component held only by one that can still move is not fully defined: the tree shows `(f)` fixed, `(-)` under-defined.
- **BOM**: components grouped by file (same path or same document id), with part number, description and material from each file's `properties.json`, in three views: top level (a sub-assembly is one line), parts only (through every level, quantities multiplied) and indented (`2`, `2.1`, `2.2`…); exported as CSV.
- **Display**: every part occurrence (a top-level component plus its path inside sub-assemblies) is moved to its placement and the meshes are combined into one for the viewport; the face and edge ranges of each occurrence map picks back to it and a persistent name.
- **Drawings** (first step, `oxyde_format::drawing`, `drawing_export.rs`, `oxyde-cli drawing`): the front, top, right and isometric views of a part (its bodies) or an assembly (its visible parts placed), hidden lines removed exactly by the kernel (`Kernel::project_edges`: OCCT `HLRBRep_Algo`, sharp, smooth and outline edges, visible and hidden, as polylines in the view's frame), laid out on an ISO A sheet in first or third angle projection at the largest ISO 5455 scale that fits, with a frame, a title block, the projection symbol and centre marks on the holes seen end on (circles found among the visible polylines), and written in pure Rust as PDF (one page, Helvetica), SVG or DXF (R12, at the views' true size, layers `VISIBLE`, `HIDDEN`, `CENTER`, `SHEET`). Nothing is saved: an export, not yet an `.oxydrw` document. Still to come: a drawing document with its own views, dimensions and annotations, a bill of materials table.

## 9. Application (`oxyde-app`) and viewport (`oxyde-render`)

Layout, SolidWorks-style: menu bar (with an Insert menu listing every feature), a tabbed **command bar** (`command_bar.rs`, like the CommandManager) with icon buttons — *Features* (Extrude, Revolve, Sweep, Loft, Fillet, Chamfer, Shell, Hole Wizard, Linear and Circular Pattern, Mirror, Reference Geometry › Plane/Axis), *Sketch* (Sketch or Exit Sketch/Discard, Smart Dimension, Line, Centerline, Corner and Center Rectangle, Straight Slot, Circle, Centerpoint, 3 Point and Tangent Arc, Polygon, Point, Trim, Extend, Sketch Fillet, Offset Entities, Convert Entities, Mirror Entities, Construction, Normal To) and *Evaluate* (Mass Properties, Measure, Section View, Equations, Rebuild; in assemblies Interference Detection too) — with undo/redo on the right; the **PropertyManager** and, under two tabs as SolidWorks' FeatureManager and ConfigurationManager, the **timeline panel** or the **configurations table** (`configurations_ui.rs`) on the left (reference planes, features with icons, status colours and tooltips, rollback bar, context menu: rename, suppress, roll back, delete), the **3D viewport** in the centre with a heads-up view toolbar (standard views, zoom to fit, Normal To), a status bar.

- **Icons** (`icons.rs`) are drawn as vector shapes on a 24-unit grid, so they stay sharp at any scale and need no image files. One palette for all of them; disabled commands are greyed. The ignored test `icon_sheet` writes every icon to an SVG file (path in `OXYDE_ICON_SHEET`) for review.

- **Render tab** (`render_ui.rs`, `oxyde_render::pathtrace`; see `docs/RENDERING.md` §6): the model meshed with `tessellate_for_export` (each part file's solid once, placed per occurrence), each face given a `Look` from its appearance and a `Finish` (`oxyde_model::Finish`, guessed from the material unless chosen per material in the panel), traced on the GPU (`gpu_trace.rs`: the same algorithm in `pathtrace.wgsl`, fed by `TraceScene::gpu_scene` and `GpuFrame`, a band of rows per dispatch sized to about 30 ms of GPU time, its final picture developed on the CPU by `develop_sums`) or, without a GPU or after any GPU error, on a thread of its own on the CPU, and shown over the viewport. The render restarts when the camera, the size, the setup, the document revision or the looks change, once the view has been still for a frame. The setup is a preference (`RenderPrefs`), not document data. Pictures are held under `MAX_PIXELS` (8 MP) so a render stays under about 1 GB.
- **Simulation tab** (`simulation_ui.rs`, `simulation_studies.rs`, `oxyde_sim`; see `docs/SIMULATION.md` §6–§8): studies of five types, as Fusion 360 offers them: static stress, thermal, transient thermal, thermal stress and topology. The tab opens on *New Study*; a model has any number of studies, the open one in `SimulationView::study` and `done` (where the rest of the tab expects it), the others parked in order with their results (`simulation_studies::Parked`); they are saved together in one `.oxysim`, each study's results in its own `.oxyres`, and the `.oxysim` next to a model opens with it. Thermal studies take *Temperature*, *Heat Power*, *Heat Flux*, *Convection*, *Radiation* and *Internal Heat* on faces (internal heat on the faces' bodies) and are solved by `oxyde_sim::solve_thermal` (scalar conduction on the same elements and contacts, the same multigrid with one mode, Newton's method for radiation, backward Euler for transient studies); a thermal stress study solves the steady temperatures, then `oxyde_sim::solve_thermal_stress` with each element expanding by `α (T − T_ref)`. Thermal properties come from the material (`Material::thermal`), else typical values (`ThermalProps::guess`), overridable per study and material group like mechanical ones. Plots add the temperature (a transient study's at the time picked, played back on a timer, coloured over the whole history's range) and the heat flux. In a static study, fixtures (*Fixed Geometry*, *Roller/Slider*) and loads (*Force*, *Pressure*, *Gravity*) are made from the selected faces and held by persistent face name (`(Occurrence, FaceName)` in assemblies) in a `Study`, with contacts between bodies and the mesh settings; it is saved as a `.oxysim` and its results as a `.oxyres` (`simulation_files.rs`, FORMAT.md §8–§9), results tied to the model by a fingerprint of every part and assembly file's definition and of the study. The model is meshed with `tessellate_for_export` on the UI thread when it changes, each face's triangles labelled. Each solid is meshed on its own: by Netgen when the kernel has it (`Kernel::volume_mesh`, first order, on a worker kernel from `open_worker` over placed copies of the solids that the study's thread frees, through `volume_mesh_watched` so its stages show in the progress and Cancel stops it, so the document can change meanwhile; boundary triangles labelled through the copies' face history, `TetMesh::append_solid`, then ten-node by `make_quadratic`), else by `oxyde_sim::mesh_solids` (a lattice mesher with boundary snapping, the fallback). Contacts (`oxyde_sim::contact`: bonded, separation, sliding, rough, offset bonded, by augmented Lagrangian with an active set) tie the bodies; *Run* finds touching faces with `detect_contacts` and bonds them when the study has none. Then `oxyde_sim::solve` solves the study (ten-node elements by default, fixtures in local frames, conjugate gradients on every core preconditioned by smoothed-aggregation multigrid, block-Jacobi as the fallback), both on a thread of their own with progress and cancel. Mechanical properties come from the material (`Material::mechanical`), else typical values for its name (`Elastic::guess`), and a study can override them per material group; the plot settings are preferences (`SimulationPrefs`). Results are a scene that replaces the viewport's (`pickable = Some((0, 0))`, pinned to the document revision as the Section View pins its own): the boundary displaced by a scale and cut into colour bands along iso-values (`oxyde_sim::bands`), one face per model face and band, with a legend and the extreme value marked; a change to the document makes them stale and the model comes back. Fixtures and loads are drawn as green and purple arrows on their faces while the plot is hidden.
- **Topology studies and the Topology tab** (`docs/SIMULATION.md` §8): a topology study takes a static study's fixtures, forces and pressures (no gravity), *Preserve Region* items and a `TopologyGoal` (the mass to keep, the thinnest member, the iteration limit, and the manufacturing controls: symmetry planes through a point, a pull direction one or both ways, `oxyde_sim::Symmetry` and `oxyde_sim::Pull`); *Run* meshes the model as for any study and calls `oxyde_sim::optimize` on the study's thread, which solves the static study once per iteration through `solve::Prepared` (prepared once, the elements' stiffness scaled by their densities). Its result, a density per element in `Done::topology`, is drawn as the `PlotChoice::Shape` plot: `oxyde_sim::shape` cuts a closed, smoothed surface at the panel's threshold (a preference with the smoothing and the faint model around it, `SimulationPrefs`), remade when one of them changes, and *Export STL* writes the same surface; `oxyde_sim::pieces` of the same cut, kept in `SimulationView::shape_pieces`, lets the panel name what sits on pieces the loads do not reach, and *Keep it in one piece* (`TopologyGoal::one_piece`) joins them inside `optimize` once the iterations are done. The Topology tab (`CommandTab::Topology`, `AsmTab::Topology`) is the same `SimulationView` with the topology studies only: choosing it opens the model's first one (`enter_topology`), its study list and New button offer topology studies alone, and it takes the viewport only while one is open (`simulation_active`).
- UI toolkit: `egui`/`eframe` 0.29, immediate mode. The app owns one `OcctKernel`; it is the only crate that chooses a backend.
- **GPU rendering** (`gpu.rs`): the viewport is drawn with wgpu (Direct3D 12, Vulkan or Metal, through eframe's wgpu backend). The part goes into an off-screen texture with 4× multisampling and a depth buffer, which egui shows like any image; sketches and annotations are painted over it by egui. Edges are screen-space quads (1.25 px, 3 px when highlighted); a second pass writes face and edge ids into an integer texture, and picking reads back the few pixels under the cursor. Shading, colours and pick rules match the software renderer, which a test checks pixel by pixel (`gpu_picking_matches_the_software_renderer`, ignored without a GPU). When the GPU cannot start, or with `OXYDE_RENDERER=cpu`, the window falls back to OpenGL and the viewport to the software renderer; Help › About tells which is in use.
- **Appearances** (`appearance_ui.rs`): colour, transparency and colour textures on faces, bodies, the part, or a component of an assembly (`oxyde_model::Appearances`, saved in `model.json`; see FORMAT.md §3). The Appearance command is a PropertyManager panel with colour presets, a transparency slider and an image picker; every change shows at once and OK records one undo step (the appearances are part of `PartDefinition`, so undo and redo cover them). The appearance is written to its target only when it was changed in the panel, so picking a material alone does not also paint the part. The application turns the appearances into one `oxyde_render::Material` per face of the scene — the texture images decoded once (`image` crate, PNG and JPEG, shrunk to 1024 px) and shared between faces and parts. Both renderers draw opaque faces first, then edges, then see-through faces back to front with blending (still pickable), and map textures *triplanarly* (projected along X, Y and Z, blended by the normal) so the kernel's mesh needs no texture coordinates. **Floor reflections** (View menu; strength in Preferences › Graphics, `Style::floor_reflection`): the faces drawn once more mirrored in a floor just under the scene, fading with height, before everything else; the GPU writes the mirrored depth first so each pixel blends once. The id passes ignore the reflection.
- **Materials** (`oxyde_model::Material`, `MaterialLibrary`; `materials.rs` and the panel's Material page in `appearance_ui.rs`): a material is a named appearance plus a density (kg/m³), in the manner of SolidWorks' and Fusion's material libraries. A part has at most one (`PartDefinition::material`); its appearance is the part's look underneath every face, body and part appearance (`Part::face_appearance` falls through to it), its density gives the mass in Mass Properties (part and assembly, parts without a material counted apart), and its name fills `properties.material` for the bill of materials. Two scopes: the **user library**, `materials.json` next to the preferences (`oxyde_format::material_library`, starter set `MaterialLibrary::standard()` until the user saves one), and the **document**, which holds a copy of the material it uses so files stay portable. The Material page lists the library by category, previews a pick live, edits name, category, density and look, and saves to or deletes from the library; right-click › Material… opens it. In an assembly, right-click › Material on components applies a library material to every part file under the selected components (the part files are rewritten, since parts are documents of their own, and the loaded copies updated; a file whose import has not applied its STEP colours and material yet, as an imported assembly writes them, first takes them from its rebuilt loaded copy with `PartDefinition::settle_imports`, so it reopens as the assembly shows it), and *Select parts with this material* selects the components made of the same material. Materials have a `source` (`MaterialSource::Library` or `Step`): the STEP reader (`SetMatMode`, `XCAFDoc_MaterialTool`) returns the `material name` and `density` Fusion 360 and SolidWorks write for each body as `StepMaterial` (`Kernel::import_step` and `read_step_assembly`; the density settled in kg/m³ by `oxyde_occt`, since OpenCASCADE hands SI-declared densities back in g/mm³), the model gives an imported part that material on its first rebuild like the colours (`ImportAppearances::material`), the import plan does the same for every part file, and `Kernel::export_step` writes a material per shape. The **Materials window** (`materials_ui.rs`; Tools › Materials…, the *Materials* command button) edits the library in one place and lists the materials in use by the open documents; saving an edited material writes it into every open part made of it (`propagate_material`: the open part as one undo step, or every part file of the assembly rewritten). Applying a material to a part with appearances of its own asks first (`Confirm::Material`, drawn over everything by `confirm_window`) and then clears them, since the material's look replaces them.
- **STEP colours**: `import_step` reads the file through OCCT's XDE layer (`STEPCAFControl_Reader` into an XCAF document, `XCAFDoc_ColorTool`), so it returns the colour and transparency of every solid and face (sRGB, as STEP stores them; faces without a colour of their own take their solid's); faces the repair step replaced are looked up on the originals. The `Import` feature's first rebuild turns them into appearances (`Import::apply_colors`, cleared afterwards and saved only while true, FORMAT.md §3): a body appearance for a lone solid making a new body, face appearances where faces differ or when the solids fuse into an existing body. `export_step` goes the other way (`Part::step_colors`: each solid's effective appearance and the faces that differ) through `STEPCAFControl_Writer`, so a coloured part survives a trip through SolidWorks or FreeCAD; the assembly reader writes each part's STEP with its colours too. Textures do not travel, STEP has none.
- **Ambient occlusion** (`Style::ambient_occlusion`, View menu, Preferences › Graphics): screen-space, from the depth of the opaque faces. The software renderer darkens each pixel by how many of twelve neighbours (two rings, `AO_RADIUS` of the image's smaller side) lie nearer the viewer by up to `AO_REACH` times that radius in millimetres, after the opaque faces and before the edges; the GPU draws the opaque faces' depth alone first, computes the same occlusion in a full-screen pass (the ring turned per pixel by interleaved gradient noise), blurs it 3×3 and multiplies the shading by it. The reflection and the id passes ignore it.
- **Configurations** (`oxyde_model::Configurations`, `configurations.rs` in the model; `configurations_ui.rs`): named variants of one part, each a map of configured dimensions to values and of configured features to suppressed-or-not, one active. The part is always built as the active one; activating another stores the part's current values into the one leaving and applies the one arriving (`Part::activate_configuration`), so the configuration remembers what was done while it was active, as in SolidWorks. They live in `PartDefinition`, so undo, redo and the file (`model.json` `configurations`, dimensions by full name) cover them without more code; a dimension driven by an equation cannot be configured.
- **Interference Detection** (`interference.rs`, assemblies): every pair of visible part occurrences whose placed boxes overlap is checked with `Kernel::boolean(Common)` on placed copies (`transform`, released after), on every core with a kernel per worker as the Section View does; a pair sharing more than 1e-6 mm³ is listed with the volume and its meshed common solid, drawn in red after the scene's own faces (unpickable) while the window is open.
- **Export** (`export.rs`, `mesh_export.rs`): File › Export › STEP, IGES, STL, OBJ, 3MF and Image. The B-rep exports take the part's solids or the assembly's visible parts as placed copies; the mesh formats share one window (format, quality presets scaled to the model, unit, STL flavour, a preview of the mesh in the viewport and a watertightness report), with one object per part or body for OBJ and 3MF (`oxyde_format::obj`, `oxyde_format::threemf`); the image is `oxyde_render::render_styled` of the viewport's scene, fitted to the picture, with the viewport's `Style`.
- **Software rendering**: `oxyde-render` is a software rasterizer (orthographic, Y-up like SolidWorks). It draws shaded faces (normals smooth within a face, crisp between faces) and edges with a depth buffer, and fills **id buffers** in the same pass, so picking the face or edge under the mouse is exact; edges win within a few pixels. The image is shown as an egui texture and re-rendered only when the camera, size, highlight or scene changes. It is the fallback when no GPU is available, and the reference the GPU renderer is tested against.
- **Preferences** (`prefs.rs`, `prefs_ui.rs`; Tools › Preferences, Ctrl+,): saved as JSON in the user's configuration folder (`%APPDATA%\Oxyde\preferences.json`), every field defaulted so old and new files load. *Graphics*: renderer and anti-aliasing (next start), colour themes and every viewport colour, edges shown or hidden and their widths, mesh quality, orientation triad. Both renderers draw from one `oxyde_render::Style`; the GPU shader reads it from its uniform buffer. *Navigation*: orbit and zoom speed, wheel direction, view animation. *Simulation*: the memory budget a study may take (8 GB by default), turned into the most nodes a mesh may have from the measured cost per node (`simulation_ui::max_nodes`); the Simulation tab's plot settings are kept here too. *Shortcuts*: every command has an id, a context (everywhere, part, sketch, assembly) and a SolidWorks-like default; the user's changes are stored by id, conflicts in the same context are shown in red, and keys with more modifiers are matched first. *Debug*: performance overlay (frame time, triangles, rebuild and solve times), what is under the pointer (index and persistent name), egui's widget outlines and inspector.
- Navigation (`MouseScheme`, Preferences › Navigation): by default right-drag orbits about the model point under the pointer where the drag started (it stays put on screen, as in SolidWorks and Creo; the view's centre when nothing is under the pointer, or when the preference is off), middle-drag or Shift+right-drag pans; the SolidWorks mapping (middle button turns, Ctrl+middle pans) and the old one (left button turns) can be chosen. By default the orbit is *constrained*: the model's Y axis stays up the screen (`Camera::orbit_about`, yaw and pitch); View › *Constrained orbit (Y up)* off gives a *free* orbit about the screen's own axes (`Camera::orbit_free_about`, which also keeps a `roll`), as Fusion 360's, and turning it on again levels the view. Wheel zoom at cursor (speed in the preferences), middle double-click or `F` zoom to fit; Front/Top/Right/Isometric views. The left button selects: a click, or a **selection box** dragged left to right for what lies entirely inside it and right to left for what it touches (as SolidWorks), decided from the id buffers of the last image (`Frame::picks_in`, `GpuViewport::picks_in`), so it takes what is visible; in an assembly a box selects components, and with a command open its faces and edges go to the command. The viewport and the tree point at each other: the face under the pointer lights up its feature (or its component) in the tree, and selecting one scrolls the tree to it.
- **Assembly mode** (`assembly.rs`, `assembly_ui.rs`): the app holds either a part or an assembly. In an assembly the command bar has an *Assembly* tab (Insert Component, Mate, Fix/Float, Reload Parts, Bill of Materials) and an *Evaluate* tab (Mass Properties of the whole assembly: volume through every sub-assembly, size, counts; Measure on the selected faces and edges where they sit; Reload Parts); the heads-up view toolbar is the same as a part's. The tree starts with the assembly's own Front/Top/Right planes and origin (component 0, `ComponentId::ASSEMBLY`, fixed at the identity, drawn in the viewport like a part's and clickable while mating), so the first parts can be mated exactly where they belong; then the components (`(f)` fixed, `(-)` can still move, a red badge when the part file cannot be opened; expand one to pick its planes or origin) and the mates (red when they cannot hold). *Mate* opens in the PropertyManager with two selection boxes filled by clicking faces and edges in the viewport or planes in the tree (two faces or edges selected beforehand fill them); the type follows the geometry (round faces and circular edges: concentric, otherwise coincident) until chosen. As in Creo's component placement, any number of mates are collected in one command: *Add this mate* (Enter) keeps the pair in a list and clears the boxes for the next, and OK adds them all and solves once. By default the parts are previewed where the mates put them as soon as both sides of a pair are picked (the list and the pair being picked, solved on a copy of the assembly: `MatePreview`); the *Preview* checkbox, remembered in Preferences › Graphics › Previews, keeps them put until OK instead, so every pair is picked where the parts sit now. The bill of materials window scrolls. Alt+left-drag moves a free component, Alt+Shift+left-drag turns it, and the mates are re-solved as it moves; *Move Component* (command bar, right-click) makes a plain left-drag do the same until Esc, and shows an XYZ handle at the selected free component, as Creo's drag handle: three arrows along the assembly's axes, of a fixed length on screen, the one under the pointer yellow; dragging an arrow slides the component along that axis alone (the pointer's movement projected on the arrow), and the mates pull it back as usual. The viewport is told the press is the handle's (`pointer_taken`), so it neither turns, grabs nor selects. Expanding a component shows its planes and origin, the mates it takes part in, and for a sub-assembly what it holds: its parts and nested sub-assemblies, which take a material or an appearance from here (right-click; the appearance is written into the sub-assembly's file, `AssemblyDoc::set_inner_appearance`, and shown through `occurrence_appearance`: the outermost component appearance on the way to a part wins), and its own mates, read-only. Undo/redo keep snapshots of the assembly.
- **Work off the UI thread** (`jobs.rs`): opening a part or an assembly, reading a STEP file, Reload Parts and coming back from editing in place run on a thread with a worker kernel (`Kernel::open_worker`, whose shapes the main kernel can use afterwards), reporting through a `Progress` to a window drawn over everything; the result (`Outcome`) is taken on the UI thread and finished there. What a job works on belongs to it meanwhile. Coming back from editing in place reads again only the files whose modification time changed (`AssemblyDoc::reload_changed_with`, stamps taken when they were read).
- **Selection is held by persistent name** (`FaceName`/`EdgeName`), not index, so it survives rebuilds.
- **Select, then command.** Commands start from what is selected: Extrude and Revolve take the sketch selected in the timeline (else the latest sketch no feature uses yet), Fillet/Chamfer the selected edges, Shell the selected faces, patterns the selected feature, Sketch the selected plane or flat face (else it asks for one, drawing the three standard planes in the viewport to click). Extrude and Revolve are one command each, with *Add material* / *Remove material* (the feature names still follow SolidWorks: `Boss-Extrude1`, `Cut-Extrude1`; cuts carry a red badge in the timeline).
- **Undo/redo** stores `PartDefinition` snapshots (the same data that is saved); one drag of a value (in a feature window or the Dimensions window) is one step.
- **Previews** (`preview.rs`): while a feature command is open (Extrude, Revolve, Fillet, Chamfer, Shell, the patterns and Mirror, Combine, reference plane and axis), the viewport shows what OK would make. Each frame the open dialog is turned into the feature it describes (`dialog_feature`, the same definition OK applies: `ExtrudeDialog::feature` and the like) and, when that changed or the part was rebuilt, built with `Part::preview`; the viewport then shows the preview's body (`shown_body`) with the faces the feature makes tinted amber, or red for a cut, an intersection or a pattern of cuts (`tint`), and a plane or axis drawn where it would be. Editing a feature shows the part as it is at that feature; when it cannot be built there, the part just before it. The PropertyManager ends with a *Preview* switch (Preferences › Graphics › Previews) and the reason the feature fails, or its warning, before OK. Picks, highlights and the tree's hover go through the shown body, by persistent name, so they work on the preview as on the part; geometry the feature itself makes is refused for it, except a fillet or chamfer face, which stands for its edge (a click takes the edge out). A preview slow to build and mesh (over 80 ms) is built again only once the value being dragged is let go. The scene key (`scene_key`) is the document revision, or the preview's own revision when it shows something else, so the section view and the STL preview, which pin the document's scene, are left alone (the preview stays off while they are open).
- **PropertyManager** (`property_manager.rs`): a command's options show at the top of the left panel, with OK (Enter) and Cancel (Esc). While it is open the timeline and viewport stay live and **clicks go to the command**: a sketch clicked in the tree becomes the sketch to extrude, edges and faces toggle in Fillet/Chamfer/Shell (a face adds all its edges), features toggle in a pattern's *Features to copy*, a plane, flat face, edge or axis fills the plane or direction. Selection boxes list the picks, each with a remove button; what the command refers to is highlighted in the viewport and the timeline. Existing features open the same way, by double-click or right-click › Edit. Planes, axes and directions can also be chosen from lists: the standard planes and axes, the reference planes and axes before the feature, and the picks. Revolve lists the sketch's lines first, centerlines on top.
- **STEP import**: File › Import STEP… (or the *Import STEP* button) adds an *Imported* feature at the rollback bar; its solids are fused with the body, and later features build on its faces, named by their position in the imported shape. File › Open (or *New part from STEP…*) on a `.step` file makes a new part from it. The file's contents are stored in the part (`imports/` in the `.oxy` archive), so the original file is no longer needed.
- **Evaluate** (`evaluate.rs`): *Mass Properties* (volume, surface area, size along the axes from the kernel's exact bounding box, topology counts) and *Measure* (area of selected faces, length of selected edges, totals, the angle between two flat faces or two straight edges and the distance between parallel faces). **Section View** (`section_view.rs`): the model cut open by a standard plane moved along its normal, as a way of looking rather than a feature. The kernel does the cut for real (a half-space box, `Kernel::make_box` placed with `Kernel::transform`, taken from every solid with `BooleanOp::Cut`; in an assembly the box is brought into each part's own coordinates with the inverse placement and the meshes combined with `oxyde_assembly::scene::combine`); the boolean's face history tells the cut faces (from input 1, coloured, their area summed) from the solid's own (from input 0, which keep their appearance). The result replaces the viewport scene the way the STL preview does (`pickable = Some((0, 0))`, the scene revision pinned until the window closes), and is recomputed when the settings or the document change, once the pointer is up. Only the solids whose bounding box the plane goes through are cut (`side_of`); the others are shown from their display mesh (an assembly's `LoadedPart::mesh`, else meshed again at the same precision, which the kernel has cached) or left out, and the cut results are meshed at the body's display deflection so the faces the cut leaves alone keep their triangulation. In an assembly the part files are cut in parallel with worker kernels (`Kernel::open_worker`, as `load_many` rebuilds them), one unit per part file so that no two threads touch the same shapes, handed out slowest first (`Unit::cost`: the faces of the solids the plane goes through, at every placement). The model's bounds are measured once per document revision, not every frame.
- Reference planes and axes are drawn over the image (translucent squares and dash-dot lines sized to the part) and can be clicked; the one selected in the timeline is highlighted, and selecting a plane then *Sketch* sketches on it. A selected standard plane is drawn too.
- Selecting a face or an edge highlights, in the timeline, the feature that created it (for an edge, the later of the two features that made its faces).
- The rollback bar is a plain line with a round handle; drag it between features.
- **Absorbed sketches**, as in Creo and SolidWorks: the sketch an Extrude or Revolve uses (the first one, if several do) is not listed on its own; it sits under that feature, behind an expand arrow.
- **Visibility** (`display.rs`): planes, the origin, sketches and reference geometry each have an eye in the timeline (and right-click › Show/Hide); View › Hide/Show (also the eye in the heads-up toolbar) turns whole kinds off. Standard planes start hidden, absorbed sketches hidden, everything else shown. Shown sketches are drawn over the part and can be clicked to select them; the origin is drawn as a small triad.
- **Animated views**: standard views, Normal To and opening a sketch turn the camera smoothly (about half a second); opening a sketch centres its geometry, as SolidWorks does.
- **Sketch mode** (`sketch_mode.rs`): editing a sketch rolls back the features after it, turns the view normal to the plane, and edits a working copy written back on exit (Escape or *Exit sketch*; *Discard* drops the changes, and a brand-new empty sketch is removed). Tools: select, Smart Dimension, line (chains; clicking an existing point closes the contour), centerline (construction line), corner and center rectangle (the centre held by construction diagonals), straight slot (two half circles and tangent lines, equal radii, a construction centerline between the centres), circle, centerpoint arc (its way round follows how the pointer turns from the start, `arc_turn`), 3 point arc, tangent arc (from the end of a line, `Tangent` to it), polygon (corners on a construction circle, sides equal), point, trim, extend, Sketch Fillet, Offset Entities, Convert Entities, Mirror Entities. Every sketch has an **origin point** where the model origin falls in its plane (a fixed construction point): it can be snapped to, selected, dimensioned and related, but not deleted. Drawing snaps, within 8 px, to existing points, to the end points, middles and centres of the **part's edges lying in the sketch plane** (including imported geometry; the new point is fixed there), to the middle of lines, to crossings of curves, and onto curves, with a glyph at the cursor; the new point keeps the relation (coincident, fixed, midpoint, on line/circle). Centres of round part edges are marked with a cross. **Convert Entities** copies a clicked part edge (line, circle, arc) into the sketch, fixed in place; edges converted one after the other share their end points (`model_refs.rs`). Nearly horizontal or vertical lines get the relation automatically. **Smart Dimension**: click one entity then empty space (a line's length; a circle is dimensioned at once by its diameter, an arc by its radius), or two entities: point–point (horizontal or vertical when lined up, else aligned), point–line (perpendicular distance), parallel lines (distance), other line pairs (angle); circles count by their centre. **Trim** previews in red the piece under the cursor, up to the nearest crossings, and removes it on click (an end piece is cut back, a middle piece splits the curve, a circle becomes an arc, a curve nothing crosses is deleted). **Extend** previews dashed the piece a line or an arc would gain at the end nearer the cursor, up to the first curve its line or circle meets beyond that end, and adds it on click; the new end point stays on the curve it reached (*on line* or *on circle*), and an end another curve is joined to does not move (`ConstrainedSketch::extend`). Dimensions are drawn with extension lines and arrows, lengths outside the shape. A click on a dimension selects it (Delete removes it), a double click edits it; the value window opens with the value selected, so after picking two entities with Smart Dimension the value can be typed at once. While a value is typed, the curves it would move are drawn dashed where it would put them (a copy of the sketch solved with it), and the window says when the other relations cannot meet it. **Mirror Entities**: select the geometry, then click the line or centerline to mirror about (the copies are drawn dashed while the pointer is on a line); each copied point is tied to its original by a *symmetric* relation (also offered for two points and a line in the right-click menu), so the copy follows later edits. **Sketch Fillet**: click the corner point where two lines meet, or the two lines one after the other, with the radius in the tool's window: the lines are cut back and an arc tangent to both is put between them, with its radius as a dimension (the next fillets of the same radius are made equal to the first instead, as SolidWorks does); a corner that relations or a length dimension refer to stays as a construction point on both lines, a virtual sharp, and the length goes on measuring to it. **Offset Entities**: click a curve to select the curves joined to it end to end (Ctrl+click adds or removes a chain), set the distance, and click on the side the copy should go, following the dashed preview: each line is kept parallel to its original, each arc and circle concentric (they share the centre point), lines tangent to an arc stay so, the first line carries the distance as a dimension and the other lines keep the same distance through an *equal distance* relation, so one value moves the whole offset (a closed contour comes out fully defined when its original is; the ends of an open chain are free). In select mode, dragging moves points, lines or circle radii live through the solver: the dragged points stay under the cursor while the rest follows when the relations allow it (else they go as near as they can), and fixed points never move. Right-click offers the relations and dimensions that fit the selection; clicking a dimension label edits its value and name, and hovering it shows its full name (`D1@Sketch1`). Geometry is coloured blue (under-defined), black (fully defined) or red (in a conflicting relation). Undo and redo inside the sketch are local to the session (a refused change keeps what Redo has); the whole edit is one undo step in the part. Save writes the sketch as drawn into the part (`commit_sketch`, one undo step) and stays in it, the file holding the rollback bar where it was before the sketch was opened; until then the open sketch's changes count as unsaved (`is_modified`), so closing or opening another file asks first.
- **Value fields** (`quantity.rs`): the dimension window, the sketch tools' windows and the commands' `DragValue`s (through `custom_parser`) read arithmetic with units after numbers (`80/2`, `3/8 in`, `45deg`): units become factors, then the text is parsed and evaluated by `oxyde_model::Expr` without names. Lengths come out in mm, angles in degrees.

## STEP assembly import

File › Import STEP assembly turns a STEP file's product structure into Oxyde documents:

1. `Kernel::read_step_assembly` (OCCT's XCAF reader) lists every distinct product once.
   A part comes back as its solids written to a STEP file of its own, in its own
   coordinates; an assembly as instances of other products with rigid placements.
   Mirrored or scaled instances become parts of their own with the motion applied.
2. `oxyde_format::step_import::plan_step_import` decides the files: one `.oxyprt` per
   part, holding a single *Imported* feature with that STEP file, and one `.oxyasm` per
   assembly placing its components where the STEP file had them. Names come from the
   products, made valid and unique (ignoring case) file names; products without a solid
   are dropped. All files go into one folder.
3. The app writes them (asking before replacing files) and opens the top level.

Mates are not in STEP files; components keep their imported positions until mated.
OCCT's STEP translators and XCAF application are not thread-safe, so the shim serializes
every STEP read and write behind one lock.
